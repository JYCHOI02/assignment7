# [T07 최종 제출물] 인증 구현 설명서 (T07-C128 ~ T07-C130)

본 문서는 과제 T07 플랜두씨 다이어리 2의 인증 시스템 구현 내역과 보안 검증 결과를 정리한 최종 설명서입니다. 
*(비밀번호, 토큰 등 모든 민감 비밀값은 엄격한 마스킹 규칙을 적용하여 작성되었습니다.)*

---

## [① 무엇으로 붙였나] (인증 기술 스택)
* **백엔드 인증 엔진**: Python Flask + `Flask Session` (서버 측 암호학적 서명 세션)
* **비밀키 관리 (T07-C113)**: `secrets.token_hex(32)`를 통한 256비트 런타임 동적 비밀키 발급 및 `.gitignore` 로컬 파일 격리
* **비밀번호 단방향 암호화**: `Werkzeug Security` 기반 `scrypt` 솔트(Salt) 해시 알고리즘 (`scrypt:32768:8:1$...`)
* **차세대 생체인증 (Passkey)**: W3C FIDO2 WebAuthn 표준 규격 및 ECDSA(ES256) 공개키 암호화 기반 스마트폰 지문/Face ID 연동
* **세션 보안 쿠키 (T07-C112)**: `HttpOnly=True`, `SameSite='Lax'`, `Session Cookie Name='pds_session'`

---

## [② 왜 그걸 골랐나] (기술 선정 이유)
1. **데이터 주권 및 개인 격리 보장**:
   * 외부 BaaS(Firebase, Supabase 등)에 종속되지 않고, 로컬 SQLite 데이터베이스 및 세션 기반으로 사용자별 데이터를 완벽히 격리(Multi-tenancy)하기 위해 독립형 백엔드 인증 아키텍처를 선택했습니다.
2. **클라이언트 사이드 XSS 토큰 탈취 방어**:
   * JWT 토큰을 브라우저 `localStorage`에 저장할 경우 XSS(크로스 사이트 스크립팅) 공격에 의해 자바스크립트로 토큰이 손쉽게 탈취되는 치명적 취약점이 발생합니다. 이를 방지하기 위해 자바스크립트가 직접 읽을 수 없는 `HttpOnly` 세션 쿠키 전송 방식을 채택했습니다.
3. **사용자 경험(UX) 및 피싱 저항성 (WebAuthn)**:
   * 매번 긴 비밀번호를 입력하는 번거로움을 없애고 모바일 QR 스캔을 통해 스마트폰의 온디바이스 지문(Touch ID / 지문인식)으로 1초 만에 안전하게 교차 로그인할 수 있도록 WebAuthn 패스키를 구현했습니다.

## [③ 어디를 어떻게 고쳤나 (T07-C128)] (핵심 소스 코드 위치)

다음 4가지 핵심 흐름이 소스 코드의 어떤 파일과 함수를 통과하는지 기술합니다:

### 1) 회원가입 (Sign Up)
* **프론트엔드**: `plan_diary-main/templates/login.html`
  * 함수: `handleRegisterSubmit(event)` (Line 183) — 폼 입력값 유효성 검사 및 `/api/auth/register` 호출
* **백엔드**: `plan_diary-main/app.py`
  * 라우트/함수: `api_register()` (Line 609, `@app.route("/api/auth/register", methods=["POST"])`)
  * 핵심 로직: 아이디 중복 검사([`T07-C98`](plan_diary-main/app.py#L614)) ➔ 비밀번호 `generate_password_hash(..., method='scrypt')` 단방향 해싱 ➔ `users` 테이블 저장 ➔ 가입 즉시 [`establish_session()`](plan_diary-main/app.py#L499)으로 안전한 세션 수립

### 2) 로그인 (Sign In)
* **프론트엔드**: `plan_diary-main/templates/login.html`
  * 함수: `handleLoginSubmit(event)` (Line 158) — 계정 정보 전송 및 메인 화면 리다이렉트
* **백엔드**: `plan_diary-main/app.py`
  * 라우트/함수: `api_login()` (Line 644, `@app.route("/api/auth/login", methods=["POST"])`)
  * 핵심 로직: 계정 열거 방지([`T07-C99`](plan_diary-main/app.py#L659)) ➔ `check_password_hash()` 검증 ➔ [`establish_session()`](plan_diary-main/app.py#L499) 호출 (세션 만료 시각 `expires_at` 및 세션 버전 `session_version` 주입)

### 3) 로그아웃 (Sign Out)
* **프론트엔드**: `plan_diary-main/templates/index.html`
  * 함수: `handleLogout()` (Line 1045) — 상단 로그아웃 버튼 클릭 시 `/api/auth/logout` 비동기 호출 후 `/login` 이동
* **백엔드**: `plan_diary-main/app.py`
  * 라우트/함수: `api_logout()` (Line 687, `@app.route("/api/auth/logout", methods=["POST"])`)
  * 핵심 로직: DB의 `users.session_version`을 1 증가시켜 과거 발급된 모든 세션 쿠키를 즉시 서버 측에서 무효화([`T07-C114`](plan_diary-main/app.py#L692)) ➔ `session.clear()` 클라이언트 세션 파기

### 4) 자료 조회 (내 다이어리 목록 Fetch 및 본인 인증 체크)
* **프론트엔드**: `plan_diary-main/static/script.js`
  * 함수: `loadPlans()`, `loadSeeData()`, `loadObservationStats()` — API 호출 시 브라우저가 서명된 HttpOnly 세션 쿠키 자동 동봉
* **백엔드**: `plan_diary-main/app.py`
  * 데코레이터: `login_required(f)` (Line 522) — 세션 내 `user_id` 존재 여부, 유효시간 만료 여부(`expires_at`), 세션 버전 일치 여부 실시간 검증
  * 인가 함수: `api_get_plans()` (Line 1508) 및 `check_plan_ownership(conn, plan_id, user_id)` (Line 576) — SQL 쿼리에 `WHERE p.user_id = ?` 파라미터를 강제 바인딩하여 타인 데이터 접근 원천 차단

## [④ 안 열리는 것을 확인한 기록 (T07-C129)] (성공 vs 거절 대조 검증)

*(주의: 모든 계정 비밀번호 및 세션 토큰은 마스킹 표기되었습니다.)*

| 시나리오 | 구분 | HTTP 요청 (Method & URL) | 요청 헤더/본문 (마스킹) | HTTP 응답 코드 및 응답 본문 |
| :--- | :---: | :--- | :--- | :--- |

## [⑤ AI와 나 (T07-C40)]

* **AI에게 맡긴 일**:
  * Flask 세션 설정 보일러플레이트 코드 작성 및 W3C WebAuthn CBOR 인코딩/디코딩 바이트 스트림 변환 로직 보조
  * 민감정보(비밀키, 세션 토큰) 마스킹 정규표현식 필터(`SensitiveDataFilter`) 구현
* **내가 직접 판단한 일**:
  * 3일차 계획 실행력 저하 분석에 따른 **뽀모도로 세분화(1회 90분 ➔ 50분) 규칙 변경 결정**
  * 보안 세션 만료 시간(기본 30분, 테스트용 10초 콘솔 동기화) 정책 수립 및 세션 만료 시 카운트다운 타이머 UI 배치 결정
  * 비인가 접근 시 단순 흰 화면 에러가 아닌 `/login` 페이지로 매끄럽게 리다이렉트시키는 사용자 경험(UX) 흐름 설계
* **AI 제안을 따르지 않은 일**:
  * AI는 초기 설계 시 외부 서드파티 BaaS 라이브러리(Firebase Auth)를 제안하였으나, 정적 호스팅 환경과의 의존성 분리 및 데이터의 로컬 SQLite 암호화 보존 원칙을 지키기 위해 이를 거절하고 **경량 Flask 내장 서명 세션 + WebAuthn FIDO2 구조**를 채택함.

## [⑥ 아직 못 막은 것 (T07-C130)] (잔여 보안 취약점 분석)

1. **IP 기반 무차별 대입 공격(Brute Force) 방지용 Rate Limiter 미구현**:
   * **기술적 영향 및 위험성**: 현재 로그인 실패 시 계정 열거 방지(T07-C99)는 적용되어 있으나, 동일 IP에서 단시간에 수만 번의 비밀번호 대입 요청을 보내는 자동화 브루트포스 공격에 대한 속도 제한(예: Flask-Limiter 분당 5회 제한)이 구현되어 있지 않습니다. 이로 인해 취약한 패스워드를 사용하는 계정이 사전 대입 공격에 노출될 수 있으며, 서버에 서비스 거부(DoS) 형태의 CPU 부하가 발생할 수 있습니다.
2. **명시적 CSRF 토큰(Double Submit Cookie / Anti-CSRF Token) 폼 검증 부재**:
   * **기술적 영향 및 위험성**: 현재 `SameSite=Lax` 속성을 통해 서드파티 사이트에서의 악의적 Cross-Origin POST 요청을 브라우저 레벨에서 방어하고 있으나, 오래된 구형 브라우저 환경이나 특수 서브도메인 탈취 시나리오에서는 브라우저의 보호가 무력화될 수 있습니다. 더욱 안전한 시스템을 위해 모든 POST/PUT/DELETE 폼 요청마다 일회용 CSRF 토큰 헤더(`X-CSRF-Token`)를 대조하는 검증 로직이 보완되어야 합니다.
