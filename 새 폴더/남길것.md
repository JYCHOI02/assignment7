## 1. 인증 구현 설명서 (6개 항목 전문)

> **캡처 포인트:** 아래 6개 번호 체계가 명확히 분리되어 있어야 하며, ⑥번 항목이 비어 있지 않아야 합니다.

### ① 무엇으로 붙였나
- 구현 방식: Web Crypto API (PBKDF2 SHA-256 해시) 기반 클라이언트 인증 & 세션 토큰 체계 (또는 선택한 Auth SDK)

### ② 왜 그걸 골랐나
- GitHub Pages 정적 웹 환경에서 외부 백엔드 서버 없이도 독립적으로 암호화 및 인가 분리가 가능하도록 구성.

### ③ 어디를 어떻게 고쳤나 (핵심 흐름 4가지)
- **가입 (Sign Up):** `auth.js` -> `handleSignUp()` (비밀번호 솔트 생성 후 해시 저장)
- **로그인 (Sign In):** `auth.js` -> `handleSignIn()` (해시 검증 후 세션 토큰 발급)
- **로그아웃 (Sign Out):** `auth.js` -> `handleSignOut()` (활성 세션 토큰 무효화 및 스토리지 정리)
- **자료 조회 (Data Fetch):** `diary.js` -> `loadUserRecords()` (현재 활성 토큰의 유저 식별자와 소유자 일치 여부 검증)

### ④ 안 열리는 것을 확인한 기록 (확인 5가지 대조)
*(아래 2번 캡처 항목과 동일하게 연동)*

### ⑤ AI와 나
- **AI에게 맡긴 일:** 인증 가드 라우팅 및 5일 통계 수식(결측치/반올림) 함수 작성
- **내가 직접 판단한 일:** 2일차 종료 후 3일차 계획 단위를 뽀모도로 방식으로 축소 변경한 결정
- **AI 말을 안 들은 일:** 복잡한 외부 OAuth 연동 제안을 거절하고, 정적 사이트 제약에 맞춘 가벼운 로컬 세션 인증 채택

### ⑥ 아직 못 막은 것 (보안 취약점 및 위험성)
- **미비점:** 무차별 대입 공격(Brute Force) 방지를 위한 계정 잠금(Rate Limiting) 미구현.
- **위험성:** 공격자가 로그인 요청을 무한히 반복 시도할 경우 비밀번호가 무차별 대입으로 유출될 수 있는 위험이 남아 있음.

## 2. 확인 다섯 가지의 성공 요청과 거절 요청 (네트워크/콘솔 캡처)

> **주의:** 모든 토큰, 비밀번호는 `eyJhb...[생략]`, `****` 형태로 가려진 상태로 캡처해야 합니다 (T07-C131).

```text
[확인 1: 비인가 접근 차단]
- 성공: [GET /dashboard] Authorization: Bearer eyJhb...[생략] -> 200 OK
- 거절: [GET /dashboard] 헤더 없음 -> 401 Unauthorized (로그인 화면으로 리다이렉트)

[확인 2: 유효 계정 인증]
- 성공: [POST /login] id: user1, pw: **** -> 200 OK (토큰 정상 발급)
- 거절: [POST /login] id: user1, pw: wrong_pass -> 401 Unauthorized ("비밀번호 불일치")

[확인 3: 로그아웃 후 세션 재사용 방지]
- 성공: [POST /logout] -> 200 OK (세션 무효화)
- 거절: [GET /records] 이전 토큰 eyJhb...[생략] 재전송 -> 401 Unauthorized ("만료된 토큰")

[확인 4: 타인 자료 접근 격리 (양방향)]
- 성공: [GET /records?owner=user1] (user1 세션) -> 200 OK (내 자료만 5건 반환)
- 거절: [GET /records?owner=user2] (user1 세션) -> 403 Forbidden ("권한 없음")

[확인 5: 타인 자료 수정/삭제 차단]
- 성공: [DELETE /records/rec_01] (본인 작성 글) -> 200 OK
- 거절: [DELETE /records/rec_99] (타인 작성 글) -> 403 Forbidden
