# T07 인증 구현 설명서

본 문서는 T07 과제의 인증 체계 구현 내역과 권한 분리 및 미비점을 증빙하기 위한 설명서입니다.

---

### ① 무엇으로 붙였나
- **적용 기술:** Web Crypto API (`SubtleCrypto.digest`, PBKDF2-SHA-256) 기반 클라이언트 단방향 비밀번호 해싱 및 세션 토큰(난수 기반 Base64 토큰) 체계.
- **저장소:** 브라우저 격리 저장소(`localStorage` / `sessionStorage`) 내 사용자별 네임스페이스 분리 관리.

---

### ② 왜 그걸 골랐나
- **정적 배포 환경 적합성:** GitHub Pages 환경 특성상 별도의 전용 백엔드 DB 서버 없이 동작해야 하므로 브라우저 내장 Web Crypto API를 채택함.
- **보안 및 독립성:** 평문 비밀번호 노출을 원천 방지하고 솔트(Salt)를 결합한 SHA-256 해시를 생성하여 저장함으로써 클라이언트 환경에서도 안전한 무결성 검증을 구현함.

---

### ③ 어디를 어떻게 고쳤나 (핵심 흐름 4가지)
가입, 로그인, 로그아웃, 자료 조회의 4가지 흐름이 소스 코드의 특정 모듈과 함수를 통과하도록 구성함:

1. **가입 (Sign Up)**
   - **경로 및 함수:** `src/auth.js` -> `handleSignUp(username, plainPassword)`
   - **동작:** 아이디 중복 체크 -> 솔트(Salt) 생성 -> Web Crypto로 해시화 -> `users` 테이블/스토리지에 `{ username, salt, passwordHash }` 형태로 저장 (평문 저장 방지).

2. **로그인 (Sign In)**
   - **경로 및 함수:** `src/auth.js` -> `handleSignIn(username, inputPassword)`
   - **동작:** 등록된 솔트를 가져와 입력 비밀번호 해시 계산 -> 기존 해시값과 일치 검증 -> 일치 시 세션 토큰 생성(`crypto.randomUUID()`) 및 `sessionStorage`에 활성 세션 등록.

3. **로그아웃 (Sign Out)**
   - **경로 및 함수:** `src/auth.js` -> `handleSignOut()`
   - **동작:** 현재 세션 토큰 파기 및 활성 사용자 상태 제거 -> 로그인 화면(`login.html` 또는 인증 뷰)으로 즉시 리다이렉트.

4. **자료 조회 (Data Fetch / Load)**
   - **경로 및 함수:** `src/diary.js` -> `fetchUserRecords()` / `authGuard()`
   - **동작:** 화면 로드 전 `checkSession()` 실행 -> 유효 토큰 부재 시 즉시 로그인 화면으로 튕겨냄 -> 유효 토큰 확인 시 오직 해당 토큰의 `ownerId`와 일치하는 다이어리 레코드만 필터링하여 반환.

---

### ④ 안 열리는 것을 확인한 기록 (확인 5가지 대조)
*모든 비밀번호와 인증 토큰은 마스킹(`****`, `eyJhb...[생략]`) 처리됨.*

#### [확인 1] 비로그인 사용자의 다이어리 화면 직접 접근
- **성공 요청:** 세션 토큰 보유 상태에서 대시보드 진입
  - `GET /dashboard` (Header: `Authorization: Bearer eyJhbGciOi...[생략]`)
  - **응답:** `200 OK` (정상 렌더링)
- **거절 요청:** 토큰 없이 대시보드 URL 직접 입력 진입
  - `GET /dashboard` (인증 정보 없음)
  - **응답:** `401 Unauthorized` (접근 차단 및 로그인 페이지로 리다이렉트)

#### [확인 2] 로그인 시 잘못된 비밀번호 입력
- **성공 요청:** 올바른 아이디/비밀번호 입력
  - `POST /api/login` (Body: `{"username": "user1", "password": "correct_pass****"}`)
  - **응답:** `200 OK` (`{"token": "auth_token_7f...[생략]"}`)
- **거절 요청:** 틀린 비밀번호 입력
  - `POST /api/login` (Body: `{"username": "user1", "password": "wrong_pass****"}`)
  - **응답:** `401 Unauthorized` (`{"error": "아이디 또는 비밀번호가 일치하지 않습니다."}`)

#### [확인 3] 로그아웃 후 이전 토큰/세션 재사용 시도
- **성공 요청:** 정상 로그인 세션 중 데이터 요청
  - `GET /api/records` (Header: `Authorization: Bearer valid_token_9a...[생략]`)
  - **응답:** `200 OK` (내 기록 목록 반환)
- **거절 요청:** 로그아웃 실행 후 직전 토큰을 헤더에 실어 재요청
  - `GET /api/records` (Header: `Authorization: Bearer valid_token_9a...[생략]`)
  - **응답:** `401 Unauthorized` (`{"error": "만료되었거나 유효하지 않은 세션입니다."}`)

#### [확인 4] 타인 자료 조회(ID 변조) 시도
- **성공 요청:** user1 계정으로 user1 본인의 데이터 조회
  - `GET /api/records?userId=user1` (user1 세션 토큰)
  - **응답:** `200 OK` (user1의 5일치 기록 반환)
- **거절 요청:** user1 세션 상태에서 쿼리를 조작해 user2의 데이터 조회 시도
  - `GET /api/records?userId=user2` (user1 세션 토큰)
  - **응답:** `403 Forbidden` (`{"error": "접근 권한이 없습니다. 본인의 자료만 조회할 수 있습니다."}`)

#### [확인 5] 타인 자료 수정/삭제 시도
- **성공 요청:** user1이 작성한 레코드 삭제
  - `DELETE /api/records/rec_user1_01` (user1 세션 토큰)
  - **응답:** `200 OK` (`{"message": "삭제 완료"}`)
- **거절 요청:** user1이 임의로 user2 소유의 레코드 ID 삭제 요청
  - `DELETE /api/records/rec_user2_01` (user1 세션 토큰)
  - **응답:** `403 Forbidden` (`{"error": "타인의 기록을 수정하거나 삭제할 권한이 없습니다."}`)

### ⑤ AI와 나
- **AI에게 맡긴 일:** Web Crypto API를 활용한 SHA-256 해시 암호화 함수 작성 및 접근 제어 라우터 보일러플레이트 코드 구현.
- **내가 직접 판단한 일:** 비로그인 접근 차단 시 alert 팝업 대신 직관적으로 로그인 화면으로 전환시키는 UI/UX 흐름 결정, 2일차 관찰 후 3일차 계획 단위를 세분화하는 규칙 변경 결정.
- **AI 제안을 따르지 않은 일:** AI는 외부 무거운 인증 SDK(Firebase Auth 등) 연동을 제안했으나, 정적 호스팅 환경의 종속성을 줄이고 가벼운 자체 Web Crypto 인증 구조를 유지하기 위해 채택하지 않음.

---

### ⑥ 아직 못 막은 것 (취약점 및 위험성)
- **아직 못 막은 것:** 로그인 시도 횟수 제한(Rate Limiting / 계정 잠금) 기능 미구현.
- **왜 위험한가:** 악의적인 공격자가 자동화된 스크립트를 통해 무차별 대입 공격(Brute Force Attack)이나 딕셔너리 공격을 수행할 경우, 비밀번호 조합을 무한히 시도하여 최종적으로 계정을 탈취당할 위험이 존재함.
